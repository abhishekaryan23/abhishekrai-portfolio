01

Virtualization and vSphere basics

A virtual machine is a complete computer made of software. VMware built the products that run thousands of them on a few physical servers. This module explains hypervisors, ESX hosts, vCenter, clusters, datastores, templates, virtual networks and vMotion, the vocabulary every later module assumes.

What you will learn

Physical vs virtual servers · type 1 and type 2 hypervisors · ESX/ESXi and vCenter · clusters, HA and DRS · datastores · templates and content libraries · port groups and distributed switches · vMotion · history from 1998 to VCF 9 · a hands-on lab

Guess first

You are not expected to know these yet. Guessing before you read helps you remember the answer when you meet it.

A cluster has five hosts and one fails at night. What brings its virtual machines back up on the other hosts?

HA restarts, vMotion migrates live.

Why can a hypervisor run many VMs at once on one server?

Sharing plus isolation.

Two hosts must see the same virtual disks for vMotion to be fast. What provides that?

Shared datastores keep disks in place.

Why virtualization exists

  • One application per physical server wasted most of each machine.
  • Virtualization runs many isolated virtual machines on one host.
  • Servers become files, so they can be copied, moved and restarted.
ELI5: Explain like I'm 5

One family living in a big building leaves most of its rooms empty. Turning the building into flats lets several households live there, each behind its own locked door. The building is the physical server, and each flat is a virtual machine.

Explain in detail

Before virtualization, data centres commonly ran one application per physical server, because two applications on one operating system could conflict over libraries, ports and patches. Many servers used only a small share of their CPU, yet each needed rack space, power, cooling and a purchase order. A new application meant ordering hardware and waiting.

Virtualization puts a thin layer, the hypervisor, between hardware and operating systems. Each VM sees virtual CPUs, memory, disks and network cards, and believes it owns a whole computer. The hypervisor keeps VMs apart, so one crashing does not take down the others.

Physical only

  • Slow to provision: order, rack, cable, install.
  • Low use of each machine.
  • A hardware fault takes the application down.

Virtualized

  • A VM can exist in minutes.
  • Many VMs share one host's capacity.
  • VMs can restart or move to another host.

This is also the foundation for everything later in the course: a self-service portal creating a VM on request is only possible because a VM is a software object that an API can create.

Why can a VM be moved or restarted on another host when a physical server cannot?

Compare with ours

Because a VM is really a set of files plus configuration, not tied to specific hardware, so any host with the same access to those files can run it.

Virtual machine vs physical server

  • A VM has virtual CPUs, memory, disks and network cards.
  • Its disks are files on a datastore; its settings are a small text file.
  • The guest operating system inside behaves as on real hardware.
Virtual machine (VM): a software-defined computer, run by a hypervisor, with its own guest operating system.
AspectPhysical serverVirtual machine
CreationOrder, rack, cableClone or deploy in minutes
Hardware changeOpen the caseEdit settings, often while running
Failure of hostApplication downRestarted elsewhere with HA
BackupAgent or image of the diskCopy or snapshot the files
Explain in detail

A VM on vSphere is stored as a folder on a datastore. The important files are the virtual disk (a VMDK file), the configuration file (VMX) and a few logs and state files. Because they are ordinary files, a VM can be cloned, copied or turned into a template.

The guest operating system is whatever runs inside: Linux, Windows and so on. VMware Tools (open-vm-tools on many Linux systems) is a helper package installed in the guest that improves drivers, allows clean shutdown from the console, and reports the guest IP address and hostname back to vCenter. Automation often depends on it: for example, to see a new VM's IP address, the tools must be running.

Virtual hardware has a version number. A VM created on a new host may not power on a very old host, which matters when you move VMs between clusters.
Snapshots are not backups. They record changes against a base disk, grow over time, and slow the VM if kept for long.

Hypervisors: type 1 and type 2

  • A hypervisor is the software that creates and runs VMs.
  • Type 1 runs directly on hardware; ESX is type 1.
  • Type 2 runs as an application on a normal operating system.
Hypervisor: software that divides one physical machine's CPU, memory, storage and network among several isolated VMs.
ELI5: Explain like I'm 5

The hypervisor is the building manager: it shares the building's space, water and power among the flats and keeps each flat locked from the others. The building is the server; each flat is a VM.

Explain in detail

Type 1 (bare metal)

Installed straight on the server. Examples: VMware ESX/ESXi, Microsoft Hyper-V, KVM on Linux. Used in data centres because there is no general-purpose OS in the way.

Type 2 (hosted)

An application on Windows, macOS or Linux. Examples: VMware Workstation and Fusion, VirtualBox. Used on laptops for testing and learning.

The hypervisor schedules virtual CPUs onto physical cores, maps VM memory onto host RAM, and presents virtual disks and network cards. Modern CPUs include hardware support for virtualization, which keeps the overhead small.

Good to know for later: a nested lab runs ESX itself as a VM inside a type 2 or type 1 hypervisor. That is how many home labs fit on one machine.

VMs on a hypervisor, containers on a runtime

Compare the layers between application and hardware.

  • Each VM carries a full guest operating system.
  • The hypervisor sits directly on the hardware.
  • Containers share one kernel, so they are lighter.
Explain in detail

In the VM column, three applications mean three guest operating systems on one hypervisor. That costs memory and boot time but gives strong isolation and lets you mix Windows and Linux. In the container column, applications share a kernel. VMware Cloud Foundation supports both: VMs for classic workloads, and Kubernetes clusters (running on VMs) for containers, which you meet in the next module.

ESX hosts and vCenter

  • ESX (also called ESXi) is the hypervisor installed on each server.
  • vCenter Server manages many hosts from one place.
  • You work in the vSphere Client in a browser, not on each host.
vCenter Server: the central management service for vSphere. It holds the inventory of hosts, clusters, VMs, datastores and networks, and provides the API.
ELI5: Explain like I'm 5

Each ESX host is a block of flats with a manager. vCenter is the property office that keeps the list of every building, flat and resident and instructs each manager. The list is the inventory.

Explain in detail

A single host can be managed alone, but features such as clusters, vMotion, HA and DRS need vCenter. vCenter is itself delivered as a virtual appliance (a prebuilt VM running Linux). Almost everything the vSphere Client does is also available through vCenter's REST API and through scripting tools such as PowerCLI. VCF Automation later talks to vCenter through this API when it creates VMs for users.

Inventory objects form a tree: a vCenter holds one or more datacenters; a datacenter holds clusters, hosts, folders, VMs, networks and datastores. Permissions are granted on objects in the tree.

Naming note: from VCF 9.0 Broadcom's documentation calls the hypervisor ESX, the name it had before the "i" was added with ESX Server 3i in 2007. Many people and older guides still say ESXi, and the product itself did not change its design. This course uses ESX host or ESXi interchangeably.

Always use the fully qualified domain name of vCenter and keep DNS correct. Many odd vSphere errors come from DNS.

Clusters, HA and DRS

  • A cluster groups hosts so their CPU and memory act as one pool.
  • vSphere HA restarts VMs on other hosts after a host failure.
  • DRS places VMs and balances load across the hosts.
Cluster: a set of ESX hosts managed as one unit, with shared resources and shared settings such as HA and DRS.
ELI5: Explain like I'm 5

A cluster is a street of buildings run as one. If a building shuts, HA reopens its flats in other buildings after a short break; DRS spreads flats so no building is crowded.

Explain in detail

vSphere HA (High Availability) monitors hosts. If a host stops responding, HA powers its VMs on again on the remaining hosts. The VMs do restart, so there is a short outage; this is not live continuity. HA needs spare capacity, called admission control, so the cluster can absorb a failure.

DRS (Distributed Resource Scheduler) chooses a host when a VM powers on and can move running VMs with vMotion to even out load. It can run fully automated or only recommend. Affinity rules keep chosen VMs together or apart, for example keeping two database replicas on different hosts.

Resource pools divide a cluster's CPU and memory with shares, reservations and limits. Many VCF Automation placement decisions are in effect "which cluster or resource pool", so these ideas return in the infrastructure module.

HA does not protect against a bad application update or data corruption. It only handles failed hosts.

Datastores and storage

  • A datastore is a logical container where VM files live.
  • Types include VMFS, NFS, vSAN and vVols.
  • Shared datastores let any host in a cluster run a VM.
Datastore: a storage location, presented the same way whatever sits underneath, in which vSphere keeps VM folders, templates and ISO images.
Explain in detail
TypeWhat it is
VMFSVMware's clustered file system on block storage such as Fibre Channel or iSCSI LUNs.
NFSA file share from a network storage system, mounted by the hosts.
vSANLocal disks of the hosts pooled into one shared datastore. Generally available since March 2014.
vVolsThe storage array manages each VM disk as its own object.

A storage policy describes needs (for example, how many copies of data vSAN should keep) and vSphere places VMs on datastores that satisfy it. This policy idea later reappears in VCF Automation as storage profiles and tags that steer where a requested disk lands.

Disks can be thin provisioned (space used as written) or thick (space reserved upfront). Thin saves space but needs monitoring so a datastore does not fill and pause VMs.

Templates and content libraries

  • A template is a master VM copy used to stamp out new VMs.
  • A content library stores templates and ISOs and syncs them.
  • Automation clones from these images instead of installing by hand.
Content library: a vCenter object that holds VM templates, OVF/OVA packages and ISO files and can publish or subscribe to other libraries.
ELI5: Explain like I'm 5

A template is a cookie cutter, and every cookie pressed from it has the same shape. The content library is the drawer of cutters that other bakeries can copy. Cookies are new VMs.

Explain in detail

To make a template, install an operating system once, update it, install tools and agents, remove machine-specific data, and convert it to a template. A clone from it can then be customised at deployment: hostname, IP address, users. Customisation is done with guest customization specifications or, on Linux, with cloud-init.

A content library can be published so other vCenters subscribe to it and receive new template versions. That keeps every site on the same golden image. VCF Automation's image mappings (a later module) point at items like these.

Patch your templates regularly. A template installed two years ago creates VMs that start two years behind on security updates.

Virtual networking: switches and port groups

  • A virtual switch connects VM network cards to each other and the outside.
  • A port group is a named set of ports with shared settings, like a VLAN ID.
  • A distributed switch is configured once and spans many hosts.
Port group: a named group on a virtual switch that defines how connected VMs reach the network, including the VLAN.
Explain in detail

A standard switch exists on one host, so you must configure it identically on every host, which is easy to get wrong. A distributed switch (vDS) is defined in vCenter and applied to many hosts, so port groups are consistent. Physical network cards on the host, called uplinks, connect the switch to the physical network.

A VM is attached by choosing a port group for its virtual network card, for example "Prod-App-VLAN120". VLAN IDs separate traffic on shared cables. Beyond this, NSX (covered in the next module) adds software-defined networks, segments and firewalls.

Port group names matter for automation. A blueprint or network profile is often matched to networks by name or by tag.

vMotion: moving running VMs

  • vMotion moves a running VM to another host without shutting it down.
  • Memory and state are copied over the network, then control switches.
  • With shared storage the disks stay put.
vMotion: live migration of a powered-on VM from one host to another, with no noticeable interruption for users.
ELI5: Explain like I'm 5

Movers copy a lived-in flat into another building while the family carries on; then they step across in a moment. The flat is the VM.

Explain in detail

While the VM runs, vSphere copies its memory to the target in rounds, re-copying pages that changed. When the remainder is tiny, the VM is paused for a moment, the last pages and device state are sent, and the VM resumes on the target. Network switches learn the new location.

Requirements in short: compatible CPUs (or an EVC mode that hides differences), the same networks on both hosts, and a vMotion network between them. Storage vMotion moves the disks to another datastore while the VM runs. Newer vSphere versions can also move between hosts with no shared storage, and between vCenters.

DRS uses vMotion automatically, and host maintenance mode uses it to evacuate a host before patching. That is how clusters are upgraded without downtime for applications.

Why can a cluster patch its hosts one at a time without application downtime?

Compare with ours

Because maintenance mode uses vMotion to move running VMs off a host first, so each host can be updated while the VMs keep running elsewhere.

Interview questions

Q1: What is the difference between a type 1 and a type 2 hypervisor?

Type 1 runs directly on hardware (ESX, Hyper-V, KVM) and is used for servers. Type 2 runs as an application on a host operating system (Workstation, Fusion, VirtualBox) and suits desktops and labs.

Q2: What does vCenter do that a single ESX host cannot?

It manages many hosts together and enables clusters, vMotion, HA, DRS, central permissions, templates, content libraries and an API for automation.

Q3: Explain HA versus DRS.

HA restarts VMs elsewhere after a host fails. DRS decides where VMs run and balances load using vMotion. One reacts to failure, the other optimises placement.

Q4: How does vMotion work at a high level?

Memory is copied to the target host while the VM runs, changed pages are re-sent, then a brief switchover moves execution. With shared storage the disks do not move.

Q5: What is a datastore and what types exist?

A logical storage location for VM files. Common types are VMFS on block storage, NFS, vSAN and vVols.

Q6: Why use templates and content libraries?

They give consistent, patched base images, and libraries publish and subscribe so many sites use the same image. Automation clones from them.

Q7: What is the difference between a standard and a distributed switch?

A standard switch is configured per host; a distributed switch is defined once in vCenter and applied to many hosts, which keeps port groups consistent.

Q8: Why is a snapshot not a backup?

It depends on the original disk and sits on the same storage. It is a short-term rollback point, and long-lived snapshots hurt performance.

What VMware Cloud Foundation is

VMware Cloud Foundation (VCF) bundles compute, storage, networking, operations and automation into one private cloud platform that you install, update and license as a unit. This module maps the parts and shows where VCF Automation fits.

The VCF stack · ESX and vCenter · vSAN · NSX · VCF Operations · VCF Automation · VCF Installer and fleet concepts · management and workload domains · Supervisor and vSphere Kubernetes Service · history from 2016 to VCF 9.1

Why a full private cloud stack?

  • Separate products meant separate installs, versions and upgrade risk.
  • VCF tests a set of components together and ships them as one release.
  • The result behaves like a cloud, run in your own data centre.
ELI5: Explain like I'm 5

Buying an engine, wheels and seats from different shops and fitting them yourself is slow, and parts may not fit. VCF is a whole car whose parts are tested and serviced together. The parts are ESX, vCenter, vSAN and NSX.

Explain in detail

Running a private cloud means choosing compute, storage and networking products, deploying them in the right order, keeping versions compatible, and patching them without breaking each other. Doing that by hand is slow and risky.

VMware Cloud Foundation takes a different approach. Broadcom publishes a bill of materials (BOM): the exact tested versions of ESX, vCenter, vSAN, NSX and the management tools in a release. Lifecycle tooling then deploys and upgrades them together. The same stack also runs in public clouds that offer VMware, which is how many companies keep one operating model across sites.

Assembled by hand

  • Many guides and versions.
  • Upgrades planned one product at a time.

VCF

  • One tested release.
  • Fleet-wide lifecycle, licensing and identity.

Why does VCF ship tested component versions together?

Compare with ours

Because compute, storage and networking products depend on each other, so a tested set lets the platform be deployed and upgraded without incompatible versions.

ESX and vCenter in VCF

  • Each cluster of ESX hosts is managed by a vCenter.
  • VCF deploys and upgrades vCenter for every domain.
  • Everything you learned in module 01 still applies.
Explain in detail

VCF does not replace vSphere; it contains it. Every domain has its own vCenter Server and one or more clusters. Broadcom's VCF 9 materials list the hypervisor as ESX, and many people still say ESXi.

What VCF adds is automation around it: the installer creates the vCenter and hosts' base configuration, and lifecycle management applies patches in a rolling way, using maintenance mode and vMotion so applications stay up.

Because VCF Automation creates VMs through the vCenter API, the objects from module 01 (clusters, datastores, templates, content libraries, port groups) are exactly what you will map and tag in the infrastructure module.

vSAN: storage from the hosts' own disks

  • Each host contributes local disks to one shared datastore.
  • Storage policies decide how many copies of data exist.
  • No separate storage array is needed.
vSAN: hyperconverged storage built into the hypervisor that pools the local disks of cluster hosts into a single datastore.
ELI5: Explain like I'm 5

Each building lends its spare shelves to one street-wide bookshelf. Every book sits in two different buildings, so if one building is closed, the book is still there. Buildings are hosts, shelves are their disks, and the street-wide bookshelf is the vSAN datastore.

Explain in detail

vSAN keeps data as objects spread across hosts, with copies controlled by a storage policy (for example, tolerate one host failure). If a host or disk fails, vSAN rebuilds the missing copies elsewhere. VMs see an ordinary datastore. VCF can also use other principal storage options, depending on the design.

Why you care: when you create a disk in VCF Automation, a storage profile maps it to a datastore and a storage policy, often a vSAN one.

NSX: networking and security in software

  • NSX creates networks, routers and firewalls as software.
  • Segments replace VLAN-bound port groups for VM networks.
  • VPCs give each team an isolated network space.
NSX: VMware's network virtualization and security platform. It provides logical switching and routing, gateways, load balancing and distributed firewalling.
ELI5: Explain like I'm 5

The roads are built once. NSX then marks private lanes, junctions and a checkpoint at every driveway with paint and signs, without digging. Roads are the physical network; lanes are segments, junctions are gateways, and checkpoints are the firewall.

Explain in detail

NSX Manager is the control plane where you define networks. Components include segments (virtual Layer 2 networks), Tier-0 and Tier-1 gateways (routers to the outside and per-tenant), and the distributed firewall that filters traffic at each VM's virtual network card.

A VPC in NSX is a self-contained network space for a team, with its own subnets and rules, carved from address space the provider allows. VCF Automation's All Apps organizations are built around VPCs, as the tenancy module explains. VCF 9.1 added Distributed Transit Gateways, which connect VPCs to the physical network from the ESX hosts with a VLAN ID, without an NSX Edge cluster.

NSX is the usual cause of network failures in automated deployments: wrong gateway, an exhausted IP range, or a firewall rule. Learn its names early.

Management and workload domains

  • The management domain runs VCF's own components.
  • Workload domains run application VMs and containers.
  • Each domain has its own vCenter and cluster or clusters.
Workload domain: a unit of compute, storage and network capacity, managed by its own vCenter, where tenant applications run.
ELI5: Explain like I'm 5

A town runs itself from a town hall district, and people live in separate districts, so a busy district never slows the town hall. The town hall district is the management domain, each other district is a workload domain, and each has its own office (vCenter).

Explain in detail

Each workload domain can have different hardware, storage and policies, for example a domain of fast flash for databases and another for general use. Domains are the building blocks that later become regions and zones in VCF Automation.

Never deploy ordinary application VMs into the management domain. Reserve it for VCF components.

ELI5: Explain like I'm 5

Explain in detail

What VCF Automation is and why

VCF Automation is the part of VMware Cloud Foundation that lets people ask for infrastructure and get it in minutes, through a catalog or code, while the platform team keeps control through policy. This module covers the problem it solves, who uses it, its history since 2012, and how its old names map to the new ones.

Why VCF Automation exists

  • Manual VM requests take days and depend on individuals.
  • Self-service gives users speed; policy keeps the platform safe.
  • Everything is repeatable and visible in one system.
ELI5: Explain like I'm 5

In a restaurant you order from a menu instead of walking into the kitchen. The kitchen follows each dish's recipe exactly, and house rules decide who may order what and how much. The menu is the catalog, the recipes are blueprints, and the house rules are policies.

Explain in detail

Without automation, a typical request goes: ticket, approval email, storage team, network team, build the VM by hand, install software, hand over. Each step waits for a person and each person makes small differences, so no two servers match. Meanwhile developers bypass the process by buying cloud services on a credit card.

VCF Automation gives the private cloud a public-cloud-like front door. Platform engineers define what can be built (blueprints), where (infrastructure mapping), by whom (projects, quotas), and under what rules (policies). Users pick an item from a catalog or call an API. The system does the rest and keeps a record.

Without it

  • Tickets and hand builds.
  • Drift between servers.
  • Shadow IT.

With it

  • Catalog and API.
  • Same blueprint, same result.
  • Quota, approval and lease rules.

Why does self-service need policy as well as speed?

Compare with ours

Because without quotas, approvals and rules, fast self-service would let anyone consume or misconfigure shared infrastructure, so policy keeps the speed safe.

Self-service, IaC and governance

  • Self-service: users request what they need from a catalog or API.
  • Infrastructure as code: resources are described in text and versioned.
  • Governance: policies enforce limits, approvals and leases.

Vocabulary: blueprint, request, deployment, resource

  • A blueprint describes what to build.
  • A request is one user asking for it.

ELI5: Explain like I'm 5

A blueprint is a recipe, a request is one customer's order, and the deployment is the meal served at that table. The resources are the separate dishes in that meal, served and cleared together.

Explain in detail

VM Apps and All Apps organizations

  • VCF 9 offers two organization types for tenants.
  • A VM Apps organization owns its own cloud accounts and cloud zones, like Aria Automation 8.
  • An All Apps organization consumes a provider-managed pool built on the Supervisor and VPCs.
ELI5: Explain like I'm 5

Explain in detail

The provider chooses the type when creating an organization. An Organization for VM Apps exists to help Aria Automation 8 users move to VCF Automation with little disruption. An Organization for All Apps is the shared-pool model. The provider manages vSphere Supervisors and gives each organization a slice through regions and quotas, and the organization consumes built-in cloud services: VMs, Kubernetes clusters through VKS, VPC networking, volumes, databases, Harbor registries, certificates and more, from a curated catalog or self-service interfaces.

In 9.0 the two types cannot share a vCenter or NSX Manager. Starting with VCF 9.1, they can share a vCenter that has a Supervisor with VPC networking turned on, after the provider turns on the Mixed Tenancy Mode feature flag; the VM Apps organization must be created and configured first.

Rule of thumb: ask what the application teams need. Only VMs? VM Apps may be enough. VMs plus Kubernetes plus isolated VPCs? Look at All Apps.

From request to deployment

Follow one request through the stages.

  • A user requests a catalog item.
  • Policy and approval decide whether it may proceed.
  • The blueprint is placed, provisioned and extended by workflows.
Explain in detail

1. The user picks a catalog item and fills in a form. 2. Policies are checked: quotas, approval, lease. 3. The blueprint is evaluated with the form inputs. 4. Placement chooses a cluster, datastore and network that match the constraints. 5. The provider integration (here vCenter and NSX) creates the resources. 6. Extensibility runs: Orchestrator workflows or ABX actions react to lifecycle events, for example to register the VM in a CMDB. 7. A deployment appears with its resources and day-2 actions.

If any stage fails, the request shows the stage that failed, which is why knowing the order helps troubleshooting. The next modules take each stage in turn.

Why does the request check policy before provisioning anything?

Compare with ours

Because stopping an unauthorized or over-quota request early is cheap, while creating resources first and undoing them would waste capacity and could breach limits.

Architecture and tenancy

One VCF Automation installation usually serves many teams. Tenancy is how the platform keeps those teams apart while they share the same hardware. This module covers the provider, organizations, the two organization types in VCF 9, regions and quotas, projects, users, groups, roles and identity, and how all of it differs from Aria Automation 8.x.

The provider runs the platform and creates the tenants (organizations).

The problem: many teams, one platform

  • A company has many teams that need cloud resources.
  • Running a separate platform per team is expensive and slow to manage.
  • Sharing one platform without boundaries lets teams see and break each other's work.
  • Tenancy gives each team its own space on shared infrastructure.
ELI5: Explain like I'm 5

Many companies share one office tower's lifts and power, but each has its own locked floor and rules. The tower's owner is the provider; each company is an organization.

Explain in detail

Multi-tenancy means one installation of software serves several independent groups (tenants). Each tenant sees only its own users, content and settings. The people who run the platform sit one level above the tenants and decide how much of the shared infrastructure each tenant gets.

Without tenancy there are two bad options. Option one: build a separate automation platform for every business unit. That multiplies upgrades, licences and admin work. Option two: put everyone in one flat space. Then the payroll team might see the web team's catalog items, one team might use all the storage, and nobody can tell who owns a forgotten virtual machine.

VCF Automation solves this with layers. The provider layer runs the platform. Organizations are the tenants. Inside an organization, projects split the work between teams and carry limits. Users and groups receive roles that say what they may do.

Isolation

Tenants cannot see each other's users, catalogs or deployments.

Sharing

The hardware underneath is pooled, so capacity is used well.

Accountability

Every deployment has an owner, a project and an organization.

A business example: a bank might create one organization per line of business so that retail and investment teams never share a catalog, while a smaller company might use a single organization and many projects.

Because teams share the same infrastructure, tenancy keeps their users, content and limits separate so one team cannot see or consume another team's resources.

Regions and quotas

  • A region groups infrastructure that organizations can consume.
  • In All Apps, a region is made of one or more Supervisors.
  • The provider assigns each organization a quota of a region.
  • In VM Apps, regions come from the cloud accounts the organization adds.
Region quota: the amount of a region's capacity (such as CPU, memory and storage) that the provider has set aside for one organization.
Explain in detail
ELI5: Explain like I'm 5

The tower's owner has buildings in several cities, and each company's lease says how much space it may use in each city. A city is a region, and the agreed space is the region quota, which the company's office manager then shares out between teams.

Think of a region as a pool of capacity in one place, for example one data center site. In All Apps organizations the capacity of a region comes from vSphere Supervisors and their zones; in VCF Automation 9.0.x a region quota draws on one Supervisor and its zone, and Broadcom lists support for more Supervisors per quota as planned. The provider connects a region, a provider gateway and an NSX Edge cluster to an organization when setting it up, then assigns a quota.

Inside the organization, the administrator splits that quota between projects and namespaces. A namespace is a resource envelope that sets limits for CPU, memory and storage, and can be given one or more VPCs for network isolation.

Projects: the working boundary

  • A project groups people with the infrastructure they may use.
  • It carries limits such as instances, CPU, memory and storage.
  • Every deployment belongs to exactly one project.
  • Teams or lines of business usually map to one or more projects.
Project: the main operational and security boundary inside an organization. It links enterprise identity groups to allocated infrastructure, quotas and naming rules.
ELI5: Explain like I'm 5

Inside its floor, a company gives each team a room with its members, budget and equipment, and every purchase is charged to one room. Each room is a project.

Explain in detail

Projects answer three questions about a request: who is asking, where may it run, and how much may they use. When a user requests a deployment, the platform records the project on it. That is why cost reports, approvals and cleanup can all be grouped by project.

Good project design

  • One project per team and environment, for example web-dev and web-prod
  • Prod projects have tighter limits and approval policies
  • Names follow a standard so they sort and filter well

Common mistakes

  • One giant project for everyone, so limits mean nothing
  • A project per person, which creates endless administration
  • Mixing dev and prod in one project

In Aria Automation 8.x and in VM Apps organizations, a project lists the cloud zones it may use, each with its own limits and a priority, and carries constraints, a custom naming template and members. In All Apps, projects and namespaces subdivide the organization's region quota.

A good rule: if two groups need different limits, different approvers or different cost owners, they need different projects.

Users, groups and roles

  • A role is a named set of rights; a user or group receives roles.
  • Roles exist at provider, organization and project level.
  • Assign roles to groups from your directory, not to single people.
  • Give the least access that still lets people do their jobs.

Identity: where users come from

  • Organizations connect to an identity provider so people use work logins.
  • Directory groups are mapped to roles and projects.

Explain in detail

You could create local users inside each organization, but that leads to forgotten accounts. A better pattern is to connect an identity provider, import or sync groups, and assign roles to those groups. When someone leaves the company and loses their directory account, their access disappears too.

Because identity attaches at the organization level, a wrongly scoped organization makes identity mapping messy. Decide your organization layout first, then wire up identity.

Broadcom documentation for All Apps organizations lists identity provider integration and managing users and groups among the organization administrator's tasks. The provider organization can also use VCF SSO, the single sign-on service of VCF Operations, and a tenant can reuse the provider's LDAP configuration or reach VCF SSO through an OIDC connection. The problem: blueprints should not know the data center

Explain in detail

Broadcom states that in VM Apps organizations the allocation of resources, such as cloud accounts, cloud zones, profiles and image mappings, is contained in the organization itself. This is the same set of objects as in Aria Automation 8.x, which is why the rest of this module applies to both.

A useful way to remember the order: connect, divide, translate, authorise.

  1. Connect: add a cloud account for each vCenter (and NSX).
  2. Divide: create cloud zones for the clusters or resource pools teams may use.
  3. Translate: create flavor mappings, image mappings, network profiles and storage profiles.
  4. Authorise: add zones to projects with limits and assign members.

If any step is missing, deployments fail in predictable ways: no zone means no placement, no image mapping means the image name cannot be resolved, no matching network means the network constraint fails.

All Apps organizations skip the first two steps because the provider has already built regions from Supervisors and allocated quota. They still need images (content libraries), VM sizes (VM classes) and networking (VPCs).

Cloud accounts

  • A cloud account is the saved connection to a platform such as vCenter.
  • It stores the address and a service credential.
  • It also finds the regions (datacenters) inside it.
  • An NSX account can be paired for advanced networking.
Cloud account: the integration between VCF Automation and a source of capacity, such as a vCenter Server. It lets the platform discover and provision resources there.
Explain in detail

You create a cloud account by giving the vCenter address and a service account. Use a dedicated account with only the privileges the platform needs, never a personal login. The platform then discovers the datacenters, clusters, resource pools, datastores and networks it can see.

Aria Automation 8.x also supported public cloud accounts such as AWS, Azure and Google Cloud. For VCF 9 the focus is vCenter and NSX; check the compatibility pages for anything else.

Cloud zones

  • A cloud zone is a set of compute resources inside a cloud account region.
  • It can have capability tags and a placement policy.
  • Projects are linked to zones; zones do not belong to projects alone.
  • Zones do not control CPU shares when the cluster is busy.
Cloud zone: a named portion of the compute capacity in a cloud account region, such as one or more clusters or resource pools, that projects can deploy to.
Explain in detail
ELI5: Explain like I'm 5

Each branch groups its ovens into named stations, with labels such as 'stone', and each customer account is allowed certain stations. A station is a cloud zone, its ovens are clusters or resource pools, the labels are capability tags, and customer accounts are projects.

Network and storage profiles

  • A network profile describes the networks available in an account region.
  • A storage profile describes datastores and their characteristics.
  • Both carry capability tags that blueprints can ask for.
  • Network profiles can also describe isolation and security groups.
Profile: an admin-defined description of cloud-specific networking or storage, with tags, that the platform uses to satisfy a blueprint's needs.
Explain in detail

A network profile lists the existing networks (port groups, NSX segments) that can be used, with their address ranges. Tags on a profile or on a single network say what they are, for example net:app or net:dmz. A profile can also define network policies such as private or public networks, on-demand networks, and security group generation.

A storage profile describes datastores and disk types. Tags such as storage:ssd or storage:vsan let a blueprint ask for a kind of storage without naming a datastore. A profile can also pick a storage policy and a default.

Capability tags and constraints

  • A capability tag labels infrastructure, such as env:prod.
  • A constraint in a blueprint asks for a tag.
  • The platform only uses infrastructure whose tags satisfy the constraints.
  • Projects can add constraints of their own that apply to every request.

# In the blueprint
constraints:
  - tag: 'env:prod'          # hard (required) by default
  - tag: 'site:london:soft'  # soft: preferred, not required
ELI5: Explain like I'm 5

Ovens carry labels such as 'stone'. A recipe can say 'must use stone' or 'prefer stone', and an unmatched 'must' stops the order. Labels are capability tags; the recipe's wishes are constraints.

Explain in detail

Tags are a key and optionally a value. Constraints are matched against infrastructure capability tags. A constraint must include the key, and can include a value, a negative marker (an exclamation mark in front, meaning "not this tag"), and a :hard or :soft suffix that says whether it is a required or a preferred match. Without a suffix a constraint is hard.

Where do capability tags go? On cloud accounts, cloud zones, network profiles and networks, and storage profiles. Where do constraints go? On machines, networks and disks in a blueprint, and at project level. Project constraints are combined with blueprint constraints, so a project can force every request onto, say, team:web infrastructure.

StyleExampleEffect
Hardtag: 'env:prod' (or 'env:prod:hard')Fail if nothing matches
Softtag: 'site:london:soft'Prefer a match, otherwise continue
Negativetag: '!env:test'Avoid infrastructure with this tag
Agree a tag naming scheme on day one: lower case, key:value, and a short list of keys such as env, site, tier, net and storage.
A typo in either the capability tag or the constraint produces a placement failure that says no suitable resource was found. Compare both spellings first.

How placement works

  • The request carries a project and a blueprint with constraints.
  • The platform lists the project's zones that match the tags.
  • It filters by capacity and project limits.
  • It picks a location using the zone's placement policy.
Explain in detail
  1. Resolve names: flavor and image names are looked up in mappings for each candidate region.
  2. Filter by tags: blueprint and project constraints are compared with zone, network and storage capability tags.
  3. Filter by limits: the project's limits for each zone (instances, memory, CPU, storage) must still have room.
  4. Rank: remaining candidates are ordered by zone priority and placement policy.
  5. Provision: the platform calls vCenter and NSX to create the resources.

When a step finds no candidates, the request fails at that step. The error text usually hints which one: a name that cannot be resolved points to mappings, no matching tags point to constraints, and a limit message points to the project.

In VCF 9.1 All Apps, when a user selects zone Automatic, VCF Automation evaluates the workload against the namespace's Infrastructure Policies and chooses a zone and cluster that satisfy the vSphere compute policy. vCenter then places the VM on a compliant host.

Interview questions

Q1: What is a cloud account?

The saved integration between VCF Automation and a source of capacity such as vCenter, using a service account, so the platform can discover and provision resources.

Q2: What is a cloud zone and what is it used for?

A named portion of compute capacity in a cloud account region. Projects are linked to zones, and zone tags and placement policy drive where machines land.

Q3: Explain flavor and image mappings.

A flavor mapping converts a size name into CPU and memory per region. An image mapping converts an image name into a real template or library item per region. They keep blueprints environment-agnostic.

Q4: How do tags and constraints work together?

Capability tags label infrastructure. Constraints in a blueprint or project ask for tags. The platform places the request only where tags satisfy the constraints; hard constraints must match, soft ones are preferences.

Q5: What are the placement policies?

At cloud zone level: Default (random host), Binpack (most loaded host with room, for dense packing), Spread (even distribution for balance and fault isolation) and Advanced (recommendations from the operations product). Projects have a separate policy for choosing between zones.

Q6: A deployment fails with an image error. How do you diagnose it?

Check that the image mapping exists for the region of the chosen zone, that the target template or library item still exists in vCenter, and that the name in the blueprint matches the mapping exactly.

Q7: How does a project limit usage?

Each project lists its zones and sets limits on instances, memory, CPU and storage per zone, with a priority order. Requests that would exceed limits are refused.

Q8: How does infrastructure work differently in an All Apps organization?

The provider builds regions from Supervisors and assigns region quota. The organization splits it into projects and namespaces. Images come from content libraries and networking from VPCs.

Q9: What are Infrastructure Policies in VCF 9.1?

Policies that combine matching criteria with a vCenter VM-Host affinity compute policy. Providers apply them to an organization's region quota so workloads land only on hosts with the required tags.

  • formatVersion says which blueprint format the file uses; use 1.

  • Quote values that start with $, { or contain a colon, such as '${input.size}'.

${resource.web.networks[0].address}First network card's address, once known
${self.resourceName}The actual name of this resource after allocation
${input.env == 'prod' ? 4 : 2}A choice made by a condition

Properties such as address and resourceName exist in the schema but get their values only after provisioning, so use them for later steps (such as cloud-init or extensibility), not for choosing placement.

Request details are also available through env bindings. The Aria Automation 8.x expression documentation lists orgId, projectId, projectName, deploymentId, deploymentName, blueprintId, blueprintVersion, blueprintName, requestedBy and requestedAt, used as ${env.projectName}. Self references such as ${self.resourceName} only have a value after the allocation phase. Check the documentation of your release before depending on one.

If two resources refer to each other, the platform cannot decide which to build first and reports a circular dependency. Break the loop by removing one reference.

cloud-init with cloudConfig

  • cloud-init runs inside the VM at first boot.
  • cloudConfig holds the instructions in the machine properties.
  • It can install packages, write files and run commands.
  • Inputs and bindings can be used inside it.

cloudConfig: |
  #cloud-config
  packages:
    - nginx
  runcmd:
    - systemctl enable --now nginx
ELI5: Explain like I'm 5

A company phone sets itself up the first time it is switched on, using a settings list the IT team prepared. The phone is the VM, the setup step is cloud-init, and the settings list is cloudConfig.

Explain in detail

cloud-init is a standard tool in most Linux cloud images. It reads user data at first boot. In a blueprint, the user data is the cloudConfig string. It must start with #cloud-config for the cloud-config format.

The image needs cloud-init installed and a way to receive the data. In vSphere this commonly means a template prepared for cloud-init with a data source set up for it. If the template does not support it, the cloudConfig is ignored. Windows images use a different tool, so the same approach does not apply directly.


cloudConfig: |
  #cloud-config
  package_update: true
  packages:
    - nginx
  write_files:
    - path: /var/www/html/index.html
      content: |
        Environment: ${input.env}
  runcmd:
    - systemctl enable --now nginx

Because the platform replaces ${input.env} before the text reaches the VM, the page shows the value the requester chose.

Never put passwords or keys directly in cloudConfig. They end up in the deployment record. Use encrypted inputs or a secret store, and rotate anything that was exposed.

A cloud-init failure does not always fail the deployment. The VM can be reported as ready while a package install failed. cloudConfigSettings in the schema controls failure and phone-home behavior, so check what your release offers if you need the deployment to wait.

Constraints inside a blueprint

  • Constraints are tag requirements on machines, networks and disks.
  • They are matched with capability tags set up by the admin.
  • A tag can be built from an input, such as env:prod.
  • Hard means required (the default); a :soft suffix means preferred.

constraints:
  - tag: 'env:${input.env}'
  - tag: 'site:london:soft'
Explain in detail

Module 05 explained capability tags and placement. In the blueprint you add the constraints. Constraints can be placed in several spots:

WhereSelects
Machine properties: constraintsThe cloud zone for the machine
Machine properties: storage: constraintsThe storage for the boot disk
Network properties: constraintsA network or network profile
Disk properties: constraintsThe storage for the disk

Building the tag from an input, like env:${input.env}, is a neat pattern: one blueprint serves dev, test and prod, and only the zone, network and storage tagged for that environment can match.

A negative constraint starts with an exclamation mark, for example '!env:test', and means "not this tag". The full form is key, optional value, then an optional :hard or :soft suffix, all inside one quoted string.

Do not duplicate what the project already enforces. If a project always forces env:dev, the blueprint need not repeat it.

Count and clusters

  • The count property creates several copies of one resource.
  • Wire it to an input so users choose how many.
  • Copies share the same definition and get unique names.
  • Disks per machine need a special per-instance setting.

web:
  type: Cloud.vSphere.Machine
  properties:
    count: '${input.count}'
    image: ubuntu-22
    flavor: small
Explain in detail

With count: 3 the platform creates three machines from one definition. The project's naming template and the deployment keep them distinct. This works for load-balanced web tiers and small clusters.

The tricky part is giving each copy its own disk. A single disk resource can be attached to only one machine. Aria Automation documentation describes the pattern for clusters of machines and disks: put allocatePerInstance: true on the resource and use count.index to pair disk number with machine number. The documented example for the generic types looks like this:


resources:
  disk:
    type: Cloud.Volume
    allocatePerInstance: true
    properties:
      count: '${input.count}'
      capacityGb: 10
  vm:
    type: Cloud.Machine
    properties:
      count: '${input.count}'
      image: ubuntu
      flavor: small
      attachedDisks: '${map_to_object(slice(resource.disk[*].id, count.index, count.index + 1), "source")}'

This pattern comes from the Aria Automation 8.x documentation. Test it in your own release before using it in a catalog item.

A high count is a quick way to hit project limits or fill a cluster. Set a maximum on the count input and rely on project limits as a second guard.

Versioning and storing blueprints

  • Save a version each time a blueprint is ready to use.
  • Release a version to make it available to the catalog.
  • Keep blueprints in a Git repository as the source of truth.
  • Never edit a released blueprint in place during business hours.
Explain in detail

The platform keeps a version history for each blueprint. Versions let you compare changes, restore an earlier one and publish only a known-good one. A catalog item points at a released version, so the file you are editing is not what users see until you release again.

Because the blueprint is text, it fits Git. Aria Automation 8.x could synchronise blueprints with a Git repository, and VCF 9 documentation describes blueprints as version-controlled in source repositories. Module 09 covers Git-backed blueprints and CI.

Testing a blueprint

  • Check the YAML syntax with a linter before you paste it.
  • Use the editor's test or validate feature to check placement.
  • Deploy to a dev project with small sizes before releasing.
  • Read the request log when a deployment fails.
Explain in detail
  1. Lint locally: yamllint blueprint.yaml finds indentation and quoting errors.
  2. Validate in the designer: the editor reports unknown properties and unresolved references. Aria Automation 8.x offered a Test button in the design canvas that checks syntax and placement and, with input values, simulates a deployment without creating anything; look for an equivalent in your release.
  3. Deploy to dev: request it in a dev project with the smallest size and count. Confirm the VM boots, cloud-init ran and the disks and networks look right.
  4. Try bad input: choose the minimum and maximum values and an unusual enum value.
  5. Release: save a version, release it, and request it through the catalog as a normal user.

When a request fails, open the deployment and then the request history. The first error line usually names the step: a mapping, a tag, a limit, or the guest.

A full annotated example: web server

One or more nginx servers on an application network, with a data disk and a page that shows the environment.


formatVersion: 1
inputs:
  env:
    type: string
    title: Environment
    enum: [dev, test, prod]
    default: dev
  size:
    type: string
    title: Size
    oneOf:
      - const: small
        title: Small (1 vCPU, 2 GB)
      - const: medium
        title: Medium (2 vCPU, 4 GB)
    default: small
  count:
    type: integer
    title: Number of servers
    minimum: 1
    maximum: 3
    default: 1
resources:
  appNet:
    type: Cloud.vSphere.Network
    properties:
      networkType: existing
      constraints:
        - tag: 'net:app'
  web:
    type: Cloud.vSphere.Machine
    properties:
      name: web
      count: '${input.count}'
      image: ubuntu-22
      flavor: '${input.size}'
      constraints:
        - tag: 'env:${input.env}'
      networks:
        - network: '${resource.appNet.id}'
      cloudConfig: |
        #cloud-config
        package_update: true
        packages:
          - nginx
        write_files:
          - path: /var/www/html/index.html
            content: |
              Environment: ${input.env}
        runcmd:
          - systemctl enable --now nginx
Explain in detail
  1. formatVersion: 1 selects the blueprint format.
  2. inputs offers three fields: environment (list), size (friendly labels) and server count (1 to 3).
  3. appNet joins an existing network carrying the capability tag net:app.
  4. web is the machine. count and flavor come from inputs. The machine constraint builds the tag env:dev, env:test or env:prod from the chosen environment.
  5. networks refers to appNet, so the network is resolved before the machine.
  6. cloudConfig installs nginx at first boot and writes a page containing the chosen environment.

For this to deploy, the admin must have prepared: an image mapping named ubuntu-22 that points at a cloud-init capable template, flavor mappings small and medium, zones tagged env:dev, env:test and env:prod, and a network or profile tagged net:app. The project must list those zones and allow the count.

Ideas to extend it: add a Cloud.vSphere.Disk for data (one machine), add a second network, move the page content into an input, or add a lease policy in Module 07.

Names such as ubuntu-22 and the tags are examples. Use the names your administrator defined.

Interview questions

Q1: What is a blueprint?

A YAML document that declares the resources of a deployment, such as machines, networks and disks, plus the inputs a requester can set. The platform builds it identically each time.

Q2: What are the main sections of a blueprint?

formatVersion, inputs and resources. Resources have a name, a type and properties.

Q3: How do inputs differ from resource properties?

Inputs are the request-time choices that become form fields. Properties configure a resource and can use inputs through expressions.

Q4: How are image and flavor resolved?

The names in the blueprint are translated by image mappings and flavor mappings defined for the region or cloud account the platform picks.

Q5: How do you make one blueprint work for dev and prod?

Add an env input and build the constraint tag from it, such as env:${input.env}. Only infrastructure tagged for that environment can match.

Q6: How do you run setup commands at first boot?

Use cloudConfig with cloud-init, provided the template supports it. Install packages, write files and run commands there.

Q7: How do you give each machine in a count its own disk?

Use a per-instance pattern with allocatePerInstance and count.index, as in Aria Automation documentation, then test it in your release.

Q8: How do you version and test blueprints?

Save and release versions, keep the file in Git, lint the YAML, validate in the designer and deploy to a dev project before releasing.

Q9: A blueprint validates but the deployment fails at placement. Why?

Validation checks structure, not capacity. Placement can fail from missing tags, no matching zone, missing mappings or project limits.

Catalog, forms and governance

A blueprint is a recipe that only its author can use. The catalog turns it into a menu item that other people can order, the custom form is the order sheet, and policies are the house rules: who must approve, how long the result may live, and what the requester may do afterwards. This module covers content sources, catalog items, custom forms, policies and the full life of a request.

Why a catalog and governance exist

  • Self-service is fast, but unlimited self-service becomes cost and sprawl.
  • The catalog offers approved items; policies add rules around them.
  • Requesters see a simple form, not YAML.
  • Admins keep control without becoming a ticket queue.

A school canteen has a menu, an order slip, and rules like "one dessert per child". Nobody walks into the kitchen.

Explain in detail

ELI5, continued: The menu is the catalog, the order slip is the custom form, and the rules are the policies. The cooks (the platform) make exactly what was ordered, the same way every time.

Before self-service, a developer who needed a server raised a ticket and waited days. Cloud platforms removed the wait, but they also removed the brake: anyone could create anything and forget it. A private cloud has a fixed amount of capacity, so forgotten virtual machines are a real cost. The catalog and policies bring the wait down to minutes while keeping three controls: what can be ordered, what must be approved, and how long things may live.

Without a catalog

  • Requests arrive as tickets or chat messages
  • Each server is built slightly differently
  • Nobody knows who owns what
  • Old machines are never removed

With a governed catalog

  • Requests arrive through one form
  • Every deployment comes from a tested blueprint
  • Owner and project are recorded
  • Leases reclaim forgotten deployments

Because capacity is limited, so the catalog makes ordering easy while policies control approval, cost and lifetime, which stops unlimited self-service from filling the cloud.

Policies: the house rules

  • A policy is a rule applied to requests or deployments that match its scope.
  • VCF 9 types: approval, lease, day 2 actions, deployment limit, resource quota, content sharing.
  • Scope is the organization, several projects, or one project, plus optional criteria.
  • Policies are checked automatically; users cannot skip them.

A common design is a few broad policies (a default lease for all, approval for production) and a few narrow exceptions for special projects.

Approval policies

  • An approval policy pauses a request until approvers decide.
  • Approvers are named users and groups, or a role such as project administrator.
  • Approver mode is Any or All, and an auto expiry decides after a number of days.
  • Request, approve and reject all appear in request history.
ELI5: Explain like I'm 5

Some canteen orders, such as a birthday cake, wait at the counter until a teacher signs the slip. If nobody signs within a set number of days, the slip is decided automatically. The teacher is the approver.

Explain in detail

ELI5, continued: The automatic decision can be yes or no, and the auto-expiry setting says which. With Any, one teacher's signature is enough; with All, every named teacher must sign. While the slip waits, nothing is cooked: the request is pending and nothing is provisioned.

When a request matches an approval policy, the deployment does not start. It waits in a pending state and approvers are notified. An approver reviews the details (who asked, what, how big, which project) and approves or rejects, with a comment. Only after approval does provisioning begin.

Typical design choices

  • When: approve only for production, for large sizes, or for expensive items. Approving everything trains people to click approve without reading.
  • Who: a group is better than a person, because people go on holiday.
  • How long: set the auto expiry trigger (days) and decision (approve or reject), so requests do not wait forever.
  • Where it triggers: on the deployment request (Deployment.Create), or on day 2 actions such as delete, power off, update or a machine resize. The change lease action cannot be put under approval.

Role based approval uses project administrators or project supervisors; if a project has neither, the policy is not applied to it. Approvers need a role that lets them manage approvals, and an email server must be configured for the notifications. If several approval policies match one request, the approvers from all of them are added, the shortest expiry wins, and a reject decision in any policy wins.

Do not make the requester an approver of their own request. The documentation does not promise a block for that case, so test it with two accounts.

Lease policies

  • A lease gives a deployment an end date.
  • At expiry the machines are powered off; after a grace period the deployment is destroyed.
  • Users can renew within the policy's limits.
  • Leases are how a private cloud reclaims forgotten capacity.
Explain in detail

A lease policy sets a maximum lease, a maximum total lease including renewals, and a grace period after expiry. The user sees the expiry date on the deployment and receives an email before it arrives (an email server must be configured). They can renew, but no single renewal may exceed the maximum lease and the sum may not exceed the maximum total lease. Without any lease policy, deployments never expire.

SettingMeaningExample
Maximum leaseDays a deployment stays active before it must be renewed14 days for test
Maximum total leaseLongest the deployment can exist, renewals included90 days
Grace periodDays after expiry to renew before destruction (default 1)2 days

Raising these values affects only new deployments. Lowering them makes existing deployments expire earlier, so change a live lease policy with care.

Use short leases for development and test, and no lease (or a very long one) for production. Pair a lease with a clear owner field so reminders reach a real person.
Expiry destroys data once the grace period ends. Make this obvious on the form for any item that holds data, and give data-holding items a longer grace period.

Day-2 action and limit policies

  • Day-2 means actions on a running deployment, such as resize.
  • A day-2 policy decides which actions each role can use.
  • A deployment limit caps CPU, memory, storage and VM count per deployment.
  • A resource quota caps what a user, project or organization uses in total.
Explain in detail

Provisioning is "day 1". Everything afterwards, for example power on and off, snapshot, resize, add disk, change lease, delete, is "day 2". Day-2 actions are covered in Module 10, but the permission to use them is a policy decision made here.

  • Allow developers to power cycle and snapshot their own test machines.
  • Allow resize only with approval, since it uses more capacity.
  • Deny delete on production deployments except for the platform team.

Two policy types keep a project inside its share of the cloud. A deployment limit policy caps the total memory, CPU count, storage and number of VMs in one deployment, and can also cap individual resources inside it. If several deployment limit policies match, the lowest value for each resource is enforced, and deployment limits are checked before resource quota and approval policies. A resource quota policy caps total consumption per user, per project or for the whole organization. When a request would exceed either, it fails early with a clear message instead of failing halfway through provisioning.

Policy rules and project quotas (Module 05) work together: quotas set the budget for a project, and policies set the behaviour inside that budget.

How a policy is matched to a request

  • Each policy has a scope (organization or projects), criteria, and an enforcement level.
  • Criteria match deployment properties such as the catalog item or a flavor.
  • One request can match several policies of different types.
  • Same type: hard beats soft, organization beats project, older beats newer.
Explain in detail

A request may be affected by an approval policy, a lease policy and a limit policy at once, because they govern different things. When several policies of the same type match, the documented processing order is: if any hard policies apply, only the hard ones are considered; organization scope ranks above project scope; and among equals the older policy ranks higher. For lease and day 2 action policies the ranked policies are then merged into one effective policy, with the highest ranked as the baseline and lower ones adding only what does not conflict (for example a lease policy with longer values than the baseline is dropped). Approval policies are not merged this way: all matching approvers are collected, the shortest expiry applies, and a reject on expiry in any policy wins. Deployment limits take the lowest value per resource. The Enforcement tab under Content and Policies, Policies shows the decision notes for each deployment.

A request from click to deployment

The path of one request through the platform.

  • The user submits the form from the catalog.
  • Policies are checked, then the blueprint is resolved and placement picks a home.
  • Provisioning runs, and extensibility subscriptions can fire along the way.
  • The result is a deployment the user can manage.
Explain in detail
  1. Request: the form values become the blueprint's inputs.
  2. Policy checks: deployment limits are checked first, then resource quotas, then approval. A limit or quota can reject the request early. An approval policy can pause it until someone approves. A lease policy attaches an expiry date.
  3. Blueprint evaluation: bindings such as ${input.size} are filled in and constraints are read.
  4. Placement: the platform picks a cloud zone, host and datastore that satisfy the constraints and quotas.
  5. Provisioning: machines, disks and networks are created in vSphere and NSX.
  6. Extensibility: subscriptions to lifecycle events can run workflows or ABX actions, for example before allocation or after provisioning (Module 08).
  7. Deployment: the result is recorded with its owner, project, lease and available day-2 actions.

If the request fails, the request history shows the stage where it stopped. This is the first place to look when troubleshooting (Module 10).

Why are policies checked before placement and provisioning start?

Compare with ours

Because it is cheaper to reject or pause a request before any capacity is used than to build something and then remove it.

Interview questions

Q: What is a content source and why do you need one?

It is a configured link that imports orderable content, such as released blueprints, Orchestrator workflows or extensibility actions, into the catalog. Without it the catalog is empty. You still have to share the imported items with a project through a content sharing policy.

Q: A user cannot see a catalog item. How do you troubleshoot?

Check that the blueprint version is released, the content source has imported it, a content sharing policy for the user's project includes the item and the user or their group, and the user is a member of that project with a role that can request.

Q: What does a custom form do that the default form does not?

It lets you reorder and group fields, relabel them, use dropdowns and other widgets, set defaults, make fields required or read-only, show fields conditionally, fill choices from an external source, and run an Orchestrator validation action on submit.

Q: How can a dropdown list come from another system?

Set the field's value options to an external source, which is a VCF Operations Orchestrator action. The action returns the list, and its inputs can be bound to other fields on the form.

Q: Name the main policy types and what each controls.

Approval (human decision before a request or day 2 action runs), lease (lifetime), day 2 actions (which actions are allowed afterwards), deployment limit (size of one deployment), resource quota (total use by a user, project or organization) and content sharing (who sees which catalog items).

Q: Why is a form not enough to enforce a rule?

A form only shapes how a person fills in the request page. Policies and blueprint logic are evaluated by the platform on every request, including requests made by scripts and tools through the API.

Q: How do you avoid approval fatigue?

Require approval only where risk or cost is high, such as production or large sizes, and approve by group so someone is always available. Approving everything makes people click without reading.

Q: Describe what happens between pressing Request and getting a deployment.

The form values become inputs, policies are checked (limits, approval, lease), the blueprint is evaluated, placement chooses a home, resources are provisioned, extensibility subscriptions fire at lifecycle events, and a deployment is recorded with its owner, project and lease.

Q: How did this change from vRealize Automation 7 to 8 and VCF 9?

In vRA 7 entitlements by business group decided visibility. From 8.x content is shared with projects through content sharing policies, and Service Broker acts as the catalog. VCF 9 merges Assembler, Service Broker and Orchestrator into one VCF Automation portal with Consume, Design and Content and Policies menus; the services behind them are unchanged.

Orchestrator: the main ideas

  • A workflow is a diagram of linked steps with inputs and outputs.
  • Elements include scriptable tasks, decisions and nested workflows.
  • Actions are reusable functions, usually JavaScript, called from workflows.
  • Plug-ins add ready-made objects such as vCenter, REST or SSH.
Workflow: a saved sequence of steps in Orchestrator, with typed inputs, typed outputs and a visual schema. Each run is recorded as a workflow run with a log.
Explain in detail

A workflow is a helper's task card: several steps, choices such as 'if the oven is full, wait', and calls to other cards. An action is one small skill written once, like 'slice bread', that many cards reuse. Plug-ins are ready-made tools, like the phone or till.

Orchestrator's JavaScript has historically been an older dialect than the one browsers and Node.js run today. Write plain var, functions and loops, and check your release's documentation before relying on newer syntax.

Workflow schema and error handling

  • The schema runs left to right from Start to End.
  • A red exception path catches errors from an element.
  • A decision reads a value and picks a branch.
  • Loops and nested workflows keep large processes tidy.
Explain in detail

You draw a workflow by dragging elements onto the schema and linking them. Each element can bind its inputs from workflow inputs, attributes or the outputs of earlier elements. If a scriptable task throws an error, the run follows the element's exception link, if there is one, or the workflow fails.

  1. Keep each scriptable task short and single purpose.
  2. Add an exception path to a "send alert" task for anything important.
  3. Use a decision to skip work that is not needed (for example only act on Linux machines).
  4. Call a nested workflow for reusable steps such as "create DNS record".
  5. Run the workflow with test inputs and read its log tab.
If you cannot read the schema at a glance, split it. Two small workflows are easier to test than one huge one.

JavaScript in Orchestrator

  • Logging uses System.log, System.warn and System.error.
  • An action receives inputs as variables and ends with return.
  • A scriptable task reads inputs and writes outputs by name.
  • Throw an Error to send the run down the exception path.

// Action: buildHostname
// Inputs:  prefix (string), env (string), index (number)
// Return type: string
var cleanEnv = env.toLowerCase().replace(/[^a-z0-9]/g, "");
var number = ("000" + index).slice(-3);

}

System.log("Built hostname " + hostname);
return hostname;
Explain in detail

An action in Orchestrator is a named function stored in a module such as com.example.naming. Its inputs (declared in the editor, each with a type) become variables inside the script, and the script ends with return of the declared type. You do not write the function header; the editor adds it around your code.

When a workflow is started by a subscription (later in this module), the platform passes the event details in as inputs. The documented pattern is a single input of type Properties named inputProperties that carries the whole payload. Your first scriptable task reads values out of it with get.

The exact keys available differ per event topic (the Compute allocation topic, for example, documents resourceNames and hostSelections, and machine events carry a customProperties map). Configuration elements and plug-ins

  • A configuration element stores named settings outside the code.
  • Admins change settings without editing workflows.
  • Plug-ins add objects for systems such as vCenter, REST and SSH.
  • Keep passwords in secure string attributes, not in scripts.
Explain in detail

A configuration element is a stored set of named attributes, grouped in folders. Typical content is the address of a CMDB, a default DNS zone or a team email address. Workflows read them, so changing a value does not need a new version of any code. They are also a good place to keep the choices for a form dropdown (Module 07).


// Scriptable task. Reads a setting from a configuration element.
// Assumes a configuration element "dnsSettings" in the folder "Company/Network".
var category = Server.getConfigurationElementCategoryWithPath("Company/Network");
var dnsZone = null;
for (var i = 0; i < category.configurationElements.length; i++) {
    var element = category.configurationElements[i];
    if (element.name === "dnsSettings") {
        dnsZone = element.getAttributeWithKey("zone").value;
    }
}
if (dnsZone === null) {
    throw new Error("Configuration element dnsSettings not found");
}
System.log("DNS zone is " + dnsZone);

The path given to getConfigurationElementCategoryWithPath is the folder path as shown in the Orchestrator client; a wrong path returns null, which is the usual cause of a "cannot read configurationElements" error. Many designers skip code and bind a configuration attribute directly to a workflow attribute in the editor. Use whichever is clearer.

Plug-ins

Orchestrator ships with plug-ins for common needs, for example vCenter (virtual machines and hosts), REST (call HTTP APIs), SSH, mail, XML and others. A plug-in adds types to the inventory and classes to the scripting API. You add a host or endpoint once (for example a REST host) and workflows refer to it by object.

Credentials for an endpoint belong in the plug-in's host configuration or a secure string attribute. Do not type passwords into a scriptable task, because scripts are readable by everyone who can open the workflow.

ABX: action based extensibility

  • An ABX action is a small function, not a diagram.
  • Runtimes are Python, Node.js and PowerShell.
  • The platform runs it on demand and passes the event data in.
  • Good for quick tasks such as a REST call or a notification.
ABX action: a short script with a handler function. The platform calls the handler with a context object and an inputs object, and uses the returned values as outputs.
Explain in detail
ELI5: Explain like I'm 5

If a workflow is a task card with many steps, an ABX action is a sticky note with one short job, written in Python, Node.js or PowerShell. The kitchen passes it the order details and reads back what it returns. The job on the note is the handler function.

ABX actions are created under Extensibility, Library, Actions. You write the script in the editor or import a ZIP package, pick the runtime, name the main function (the default is handler; for a ZIP it is file and function, such as main.handler), define inputs, and add dependencies (a requirements.txt for Python, a package.json for Node.js, PowerShell Gallery modules for PowerShell). Actions are project-specific and can be shared with other projects. They run on a function-as-a-service runtime: the one built into the appliance, or AWS Lambda if you have configured that as an endpoint. Secrets are added as project-level secrets and read in code, so they are not stored in the script.

ABX handlers in three languages

  • Python defines handler(context, inputs) and returns a dict.
  • Node.js exports a handler with context, inputs and a callback that delivers the outputs.
  • PowerShell defines a function named handler with two parameters.
  • Returned keys become the action's outputs.

def handler(context, inputs):
    names = inputs.get("resourceNames", [])
    print("Post-provision hook saw: " + ", ".join(names))
    return {"count": len(names), "status": "done"}
Explain in detail

Python

The file defines handler. inputs behaves like a dictionary, so inputs.get("key", default) is safe when a key may be missing. Whatever you print goes to the action's run log. The returned dictionary is the action's outputs.

Node.js


exports.handler = (context, inputs, callback) => {
  const names = inputs.resourceNames || [];
  console.log("Post-provision hook saw: " + names.join(", "));
  callback(undefined, { count: names.length, status: "done" });
};

This is the shape of the editor's default Node.js template: the third argument is a callback, and the outputs are passed as its second argument. Compare it with the template your release generates when you click New Action.

PowerShell


function handler($context, $inputs) {
    $names = $inputs.resourceNames
    Write-Host ("Post-provision hook saw: " + ($names -join ", "))
    $outputs = @{
        count  = @($names).Count
        status = "done"
    }
    return $outputs
}

All three do the same thing: read a list of names from the event, log it and return a count and a status. In PowerShell the documentation says the output is the last value the function produces, so return one hashtable. The input name resourceNames is an example. Run the action once with a test input to see which keys your event topic really supplies.

Keep secrets out of action code. Add them as project secrets or action constants and read them in code (for example context.getSecret(inputs["mySecret"]) in Python), so values are not stored in plain text in the script.
ABX actions have a time limit (a configurable timeout). A long job, such as waiting for a slow system, belongs in Orchestrator or in a pattern where the action starts the job and returns.

The Event Broker and subscriptions

  • The platform publishes events at each step of a request.
  • Each kind of event has a topic, such as Compute post provision (id compute.provision.post).
  • A subscription says: when this topic fires and the condition matches, run this.
  • The target is an Orchestrator workflow or an ABX action.
Subscription: a rule with an event topic, optional filter conditions, a runnable (workflow or action), a priority, and a blocking setting.
ELI5: Explain like I'm 5

The kitchen calls out each stage, like 'dish plated'. A note on the wall says which helper reacts to which call.

Explain in detail

ELI5, continued: Each call is an event, and the stage it names is the topic. Each note is a subscription: it can add a condition such as 'only for table 5', name the helper's task (a workflow or action), and say whether the dish waits for the helper (blocking).

The component that carries the events is the Event Broker Service. When a request reaches a lifecycle stage, it publishes an event with a payload (the details). Subscriptions are looked up by topic, filtered by their condition, then run: blocking ones first in priority order, then all non-blocking ones together.

Explain in detail

Imagine a pre-allocation subscription that sets a company-standard hostname. It must be blocking, because the request needs the new name before it creates the machine. A blocking workflow writes values back through workflow outputs whose names and types match the writable event parameters of the topic: for example an output resourceNames (Array/string) on Compute allocation to rename machines, or an output customProperties (Properties) to add properties. Parameters marked read-only on the subscription page cannot be changed. An ABX action does the same by returning those keys in its output dictionary.

Extensibility as a gated pipeline

A pipeline of stages where a failing stage stops everything after it. A blocking subscription works the same way inside a request.

  • Stages run in order, left to right.
  • A failing stage stops the run, like a failing blocking handler.
  • Non-blocking handlers sit beside the pipeline and do not stop it.
Explain in detail

The animation shows a software delivery pipeline, but the shape is the same as a provisioning request with subscriptions. Each stage must succeed for the next to start. A blocking subscription is such a stage: until it passes, the request does not move on, and if it fails, nothing after it runs. A non-blocking subscription is a side job started at that point that the main flow does not wait for.

This is why blocking subscriptions should be used for checks and changes that the request really depends on, and non-blocking ones for everything else.

Interview questions

Q: What is the difference between Orchestrator and ABX?

Orchestrator is a visual workflow engine with JavaScript, plug-ins and long-running logic. ABX runs a single script function in Python, Node.js or PowerShell. Use ABX for short tasks and Orchestrator for multi-step processes.

Q: What is an extensibility subscription?

A rule that listens for an event topic, optionally filters on conditions, and runs a workflow or ABX action when it matches. It has a priority and can be blocking or non-blocking.

Q: Blocking or non-blocking: how do you choose?

Blocking when the request must wait for your result or you need to change values or veto the request. Non-blocking for notifications, auditing and other side work.

Q: What is the signature of an ABX Python action?

def handler(context, inputs): it receives a context object and an inputs dictionary, and returns a dictionary whose keys become outputs.

Q: How do you log in an Orchestrator script?

System.log for information, System.warn for warnings and System.error for errors. The messages appear in the workflow run log.

Q: What is the difference between a workflow input and an attribute?

An input is supplied by the caller when the run starts. An attribute is an internal variable shared by the workflow's elements and is not visible to the caller.

Q: Why use configuration elements?

They keep settings such as endpoints and zone names outside the code, so an admin can change them without editing or re-releasing a workflow.

Q: A subscription does not seem to run. What do you check?

That it is enabled, the topic is correct, the condition matches the test deployment, the owner or service account is valid (especially after an upgrade), and then the run history for errors.

Q: What does compute.provision.post mean?

The id of the Compute post provision event topic, fired after each machine is provisioned. A subscription on it can run follow-up tasks such as registering the machine in a CMDB. Confirm available topics in your own organization and release.

Q: How does a blocking workflow change a value in the request?

It declares a workflow output with the same name and type as a writable event parameter, for example resourceNames or customProperties, and assigns to it. The subscription must be blocking, and the topic must be blockable.

Q: What is Orchestrator called in VCF 9 and where do you open it?

VCF Operations Orchestrator (previously VMware Aria Automation Orchestrator). It is embedded in VCF Automation and opens from the Orchestrator tab in a VM Apps organization or the Orchestrate tab in an All Apps organization. External instances can be added as integrations.

The REST API and how authentication works

  • An API token is created in the portal and works like a long-lived password.
  • You exchange it for a short-lived bearer token at your organization's token endpoint.
  • Every later request carries the bearer token in the Authorization header.
  • Treat the API token as a secret and never commit it to Git.
ELI5: Explain like I'm 5

At the library desk you show your card and get a visitor sticker valid for one hour; staff then check only the sticker. The card is the API token, the sticker the bearer token.


# 1. Exchange the API token (refresh token) for a bearer token (VCF Automation 9)
$ TOKEN=$(curl -s -X POST "https://$VCFA_HOST/tm/oauth/tenant/$VCFA_ORG/token" \
    -H "Content-Type: application/x-www-form-urlencoded" -H "Accept: application/json" \
    -d "grant_type=refresh_token&refresh_token=$VCFA_API_TOKEN" | jq -r .access_token)

# 2. Use it on every other call
$ curl -s "https://$VCFA_HOST/iaas/api/projects" \
    -H "Authorization: Bearer $TOKEN"
Explain in detail
Bearer token: a string that proves who you are for a short time. Whoever "bears" (holds) it is treated as that user, so it must stay private.

Broadcom's VCF Automation API reference (developer.broadcom.com, both organization types) documents POST /tm/oauth/tenant/{tenant}/token with a form-encoded body grant_type=refresh_token&refresh_token=<API token>. The tenant is your organization name. The JSON reply holds access_token, token_type (Bearer) and expires_in of 3600, so the bearer token lives for one hour. Later calls send Authorization: Bearer <token>.

The 9.0 reference for the VM Apps provisioning service also still lists the older POST /iaas/api/login, which takes a JSON body with refreshToken and returns token and tokenType; it is described as being for local users. Prefer the tenant token endpoint above for VCF 9 and check the reference for your version.

The Terraform provider's VCF Automation token guide gives the portal steps for both VM Apps and All Apps organizations: log in to your organization, open the organization name at the top right, choose My Account under User Settings, open the API Tokens tab, click New, name the token, create it and copy it immediately, because it cannot be shown again.

Older Aria Automation 8.x guides use a different login (/csp/gateway/am/api/login) and a different token source. Do not mix instructions across versions. The API reference is organized per organization type, so check the section for your organization type and your version before copying a path. A Broadcom Knowledge Base article also notes that a token made from a user's API token has only view rights on users, groups and roles; identity changes need a service account.
A lab with a self-signed certificate makes curl fail with a certificate error. Fix the trust chain if you can. If you must skip verification in a throwaway lab, curl -k does it, but never in production.

The bearer token expires after about an hour, so long scripts should log in again when they receive a 401 response.

Explain in detail

# .github/workflows/blueprint-ci.yml
name: blueprint-ci
on:
  pull_request:
    paths:
      - "blueprints/**"
      - "terraform/**"
  push:
    branches: [main]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Lint blueprint YAML
        run: pip install yamllint && yamllint blueprints/
      - uses: hashicorp/setup-terraform@v3
      - name: Validate Terraform
        run: |
          terraform -chdir=terraform init -backend=false
          terraform -chdir=terraform validate

  apply:
    needs: validate
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    env:
      TF_VAR_vcfa_url: ${{ vars.VCFA_URL }}
      TF_VAR_vcfa_org: ${{ vars.VCFA_ORG }}
      TF_VAR_vcfa_api_token: ${{ secrets.VCFA_API_TOKEN }}
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform -chdir=terraform init
      - run: terraform -chdir=terraform apply -auto-approve

This is a starting shape: the validate job needs no access to VCF Automation, so it is safe on pull requests from anyone. Only the apply job gets the token, and only on main. The runner must be able to reach your VCF Automation endpoint. A private cloud is often not reachable from public hosted runners, so teams commonly use a self-hosted runner inside the network.

Interview questions

Q1: How does a script authenticate to the VCF Automation API?

It uses an API token created in the portal under My Account. The script posts the token to the organization's token endpoint with the refresh_token grant, receives a bearer token that lives about an hour and sends that in the Authorization header on every later call. The API token is a secret and is stored in a secret store, not in code.

Q2: Why is a 201 response to a deployment request not the end of the story?

It means the request was accepted. Approval, placement, provisioning and extensibility still run afterwards, so the script has to poll the request or deployment until it succeeds or fails.

Q3: What does the vra Terraform provider add over using curl?

Declarative configuration, a plan before changes, recorded state, dependencies between resources and the ability to destroy what it created. It calls the same API underneath.

Q4: What is the difference between blueprint_id and catalog_item_id in vra_deployment?

blueprint_id requests directly from a blueprint, so it can bypass the catalog and its form. catalog_item_id requests the published catalog item. The two arguments conflict, so you set only one.

Q5: When would you use Terraform and when Ansible with VCF Automation?

Terraform requests and tracks deployments and other infrastructure objects. Ansible configures software inside the machines that result, or calls the API from a playbook. Teams often use both in sequence.

Q6: Why connect an IPAM tool?

So addresses and DNS names come from the single source of truth, duplicates are avoided and addresses are released when deployments are deleted.

Q7: Why store blueprints in Git?

Review through pull requests, history of every change, rollback, and a base for CI checks. The portal copy is then derived from Git, not the other way round.

Q8: What would you put in a CI pipeline for blueprints?

YAML lint, terraform validate and plan on pull requests, with no access to the platform. An apply job on main with a service account and secrets from the CI system, ideally on a self-hosted runner that can reach the private endpoint.

Aria Automation 8.x documentation warns that power actions are normally safe, while others such as adding a disk need care: if you add a disk with a day-2 action and later apply an updated blueprint to the same deployment, the blueprint can overwrite the change. A Broadcom Knowledge Base article for Aria Automation 8.18.x also reports that the out-of-the-box Add Disk action does not automatically honor storage constraints unless the user specifies the storage tag.

No single VCF 9 page lists every default day-2 action for every organization type, and the actions shown depend on the resource type, your role and the day-2 policies in force, so open a deployment in your portal to see the actions it actually offers. Resizing has hypervisor rules too: some guest configurations cannot change CPU or memory while running.

Delete is permanent. Confirm the right deployment, check the owner, and take a final backup if the data matters.

Custom resources and resource actions

  • A custom resource represents something the platform does not model by default.
  • A resource action adds a new button to an existing resource type.
  • Both are backed by an Orchestrator workflow or an ABX action.
  • Always use platform-aware actions so its state stays correct.
ELI5: Explain like I'm 5

Standard services cover jobs like repainting. A resource action adds a new service, like 'check the boiler'; a custom resource adds something new to track, like a mailbox.

Explain in detail

ELI5, continued: Each new service is carried out by your own Orchestrator workflow or ABX action, and it is booked through the letting office (the platform) so the office's records stay right. Doing the job behind the office's back leaves those records wrong.

A resource action attaches a workflow to a resource type, for example a "Reboot with health check" action on machines. The action receives the machine as an input and runs your logic. A custom resource goes further: it defines a new type, such as a DNS record or a firewall rule entry, with create, update and delete workflows, so that the platform can track it inside a deployment.

Where these live in the menus differs between Aria Automation 8.x and VCF 9 and between organization types, so locate the equivalent in your version. The idea is the same: a form for inputs, a workflow or action for the work, and a policy for who can run it.

Broadcom documents one trap clearly (Knowledge Base, VCF Automation 9.0.2). If a custom power workflow calls the generic vCenter power workflow, vCenter changes at once but the platform's deployment status can stay stale for around 10 to 15 minutes. The advice is to take the machine as the platform's own machine type and use the machine power actions from the platform's infrastructure package. In short: act through the platform, not around it.

After an upgrade, check that custom actions still appear in the menus. A Broadcom Knowledge Base article records custom resource actions disappearing from the machine and deployment menus after the 9.0 to 9.1 upgrade because the mapping to their Orchestrator workflows broke; the fix is to refresh each action's mapping by hand.

  • A person or automation reacts, and the measurement comes back down.
  • Resizing or scaling a deployment is one possible reaction.

Placement

The blueprint's constraints ask for something no zone offers, for example a tag spelled differently on the zone and in the blueprint. Compare the constraint text with the capability tags exactly.

Limits on the project or a policy deny the request. The message normally names the limit. Raise it only if the request is legitimate.

Network

A subscription ran a workflow that failed. If the subscription is blocking, the whole request waits for it and fails with it. Read the run log, check the inputs it received, and check any credentials or endpoints it uses.

Cloning a template from a content library can fail for reasons unrelated to automation, such as a full datastore or a missing permission for the service account. Reproduce the clone by hand in vCenter to separate platform problems from infrastructure problems.

A method for diagnosing a failed request

  • Find the stage that failed; do not start from the final message.
  • Read the detail for that stage and the layer just below it.
  • Change one thing at a time and retry.
  • Write down what fixed it for next time.

1. Locate

Which stage failed: policy, placement, provisioning or extensibility?

2. Read

Open the error detail and the matching run or task in the layer below.

3. Fix and retry

Change one thing, request again, compare the result.

Explain in detail

The request pipeline from Module 03 (catalog, policy, blueprint, placement, provision, extensibility, deployment) is also your troubleshooting map. A failure before placement points to policy, quota or blueprint syntax. A failure in placement points to constraints and capacity. A failure after provisioning starts points to vCenter, NSX or the guest. A failure at extensibility points to workflows.

A quick way to separate causes is to request a simpler blueprint with one VM, one network and no custom steps. If that works, the difference between it and the failing blueprint is where to look.

Changing several settings at once makes it impossible to know which one fixed the problem, and it can create new faults. Change one thing, retry, and record the result.

Platform health and support bundles

  • In VCF 9 the automation platform runs as a Kubernetes cluster on VMs.
  • Platform problems look different from a single failed request.
  • VCF Operations Fleet Management tracks lifecycle tasks and errors.
  • A support bundle collects logs for Broadcom support.
ELI5: Explain like I'm 5

If one tap drips, you fix that tap. If every house on the street loses water at once, you check the water supply, not each tap. The taps are single deployments, and the water supply is the automation platform.

Explain in detail

Broadcom's articles and training for VCF 9.0 describe the VCF Automation platform as a cluster of VMs running Kubernetes (the VCF Services Platform, VMSP). A troubleshooting course outline for VCF 9.0 covers the cluster architecture, the log files used when the cluster is provisioned, key kubectl commands for checking cluster health, and the structure of the support log bundle.

Signs of a platform problem are many unrelated requests failing, the portal being unreachable, or Fleet Management tasks showing errors during lifecycle work. Fleet Management shows lifecycle tasks, for example under Lifecycle then VCF Management then Tasks, and error codes in those tasks are searchable in the Broadcom Knowledge Base.

Support bundles are produced from the lifecycle view in VCF Operations (Fleet Management in 9.0, Fleet Lifecycle in 9.1) or through the services runtime API when that view is unavailable. Knowledge Base articles describe bundle generation failing when the stored password for the appliance's system user no longer matches the real one, so keep appliance credentials current. Commands that modify the cluster should be run only as Broadcom support directs.

Do not edit the platform's Kubernetes objects by hand. The platform reconciles its own configuration with Flux (a GitOps tool), and a Broadcom Knowledge Base article notes that a manual patch to a managed object is reverted on its own because drift detection stays on. Only make an edit that a Knowledge Base article documents, and open a support case with the bundle otherwise.

Interview questions

Q1: What is a day-2 operation?

Any change or action on a deployment after it was created: power, resize, snapshot, add disk, extend lease, delete, or a custom action. In a governed platform these are requests too, so policies and approvals apply.

Q2: Why should day-2 changes go through the platform?

The platform keeps its own record of each deployment. Changes made directly in vCenter leave that record stale, which causes wrong status, failed later actions and broken governance.

Q3: What is the difference between a resource action and a custom resource?

A resource action adds an operation to an existing resource type. A custom resource defines a new type with lifecycle workflows so the platform can create, track and delete it.

Q4: A user says "my request failed". What do you do first?

Open the deployment history and request detail, find which stage failed, then read the error for that stage and the matching task or run in the layer below: Orchestrator, vCenter or NSX.

Q5: Name the five common failure families.

Placement, quota or limits, image or size mapping, network, and workflow or script errors.

Q6: How would you separate a platform problem from a blueprint problem?

Request a minimal blueprint with one VM and no custom steps. If it works, the fault is in the original blueprint. If many unrelated requests fail, check the platform's health and Fleet Management tasks.

Q7: What do you do before upgrading the platform?

Read the release notes and Knowledge Base for the exact version path, make sure prerequisites such as the required 8.x version are met, back up, list all custom integrations to test, and plan the upgrade as its own workstream.

Q8: Why change one thing at a time while troubleshooting?

So you know which change made the difference and avoid introducing new faults while hunting the old one.

1. ESX runs directly on server hardware with no general-purpose operating system underneath. What kind of hypervisor is it?

ESX is a type 1 hypervisor.

2. A host fails and the VMs on it restart on other hosts in the cluster. Which feature did this?

HA restarts, DRS balances, vMotion moves running VMs.

3. Which VCF component provides software-defined networking and distributed firewalling?

NSX is the network and security layer.

4. Which is the correct order of the product's names over time?

The product line moved from vCloud Automation Center to VCF Automation across several names.

5. In VCF Automation tenancy, who sets aside capacity for an organization?

The provider gives each organization a share of capacity.

6. What is a cloud zone?

A cloud zone is a slice of capacity inside a cloud account.

7. In a blueprint, what does flavor: ${input.size} do?

A binding like this reads the request input at deploy time.

8. Which policy would delete test deployments automatically after 14 days unless the owner extends them?

Leases handle expiry; approvals handle permission.

9. A subscription is blocking. Its workflow fails. What is the effect on the request?

Blocking subscriptions hold the request until they finish.

10. A script wants to call the VCF Automation API. What does it send on each call after logging in?

Exchange the API token once, then send the bearer token.

11. With the Terraform vra provider, which resource asks for a deployment from a blueprint?

vra_deployment requests and tracks a deployment.

12. A request fails and the message is vague. What should you do first?

Locate the stage, read the detail, change one thing, retry.
